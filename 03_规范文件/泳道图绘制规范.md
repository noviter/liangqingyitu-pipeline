# 业务泳道图绘制规范

本规范从《附件：广东省交通运输厅一体化数字平台业务泳道图编制工作指引.docx》沉淀而来，用于“两清一图”阶段 3 自动绘图。规范只约束图形结构、符号和校验，不提供具体业务答案。

## 1. 图形边界

- 一张图表达一个完整业务流程；流程过复杂时，可按阶段拆成多页或用复合活动表示子流程。
- 每个业务事项生成一个 Draw.io 页签，页签名为“行xx-事项名称”，标题为“业务事项：事项名称”。
- 本项目默认采用纵向泳道：流程从上往下推进，跨泳道连线横向连接，避免横向长图难以阅读。

## 2. 池和泳道

- 池代表一个系统、子系统，或一个不依赖系统的参与方。
- 当池代表厅内系统时，系统名称必须与“应用清”或本次 H 列系统名称对齐。
- 泳道是池内的角色分区，代表系统中的用户角色，或非系统参与方中的业务角色。
- 系统、平台和数据库可以作为池或节点支撑说明，但不得作为泳道主体，不得替代发起、办理、审核、反馈等业务角色。
- 外部参与方内部过程对本事项没有影响时，可作为黑箱池，只画与本流程有关的收发消息和结果。

## 3. 基本元素

- 开始事件：细线圆圈。每张业务泳道图必须有且只有一个开始事件。
- 结束事件：加粗圆圈。每个池至少应有一个结束事件；没有独立结束依据时，应在同一主流程终点设置明确结束。
- 活动：圆角矩形。一个活动节点只表达一个业务动作，如填报、提交、受理、审核、退回、汇总、分析、发布、归档。
- 网关：菱形。用于判断、分支、合并和连接。只有 F/I 列明确支持判断条件和路径时才画网关。
- 中间事件：圆圈加文字，用于收到通知、收到反馈等影响流程但不开始或终止流程的事件；必须标注文字。
- 注释或文件元素只在确有助于理解时使用，不得代替流程节点。

## 4. 连线规则

- 控制流表示同一池内活动和事件的先后顺序，用实线箭头。
- 消息流表示不同池之间的信息、材料、数据或通知交换，用虚线箭头，并标注消息内容。
- 跨池流转不得用实线直接穿越多个池；应使用消息流说明提交、分发、反馈、通知或数据交换。
- 网关出口两条时，应标注“是/否”“通过/不通过”等条件；出口三条及以上时，宜编号并标注条件。
- 已有依据的退回补正必须标明退回对象和回流节点；没有依据的退回路径不画，写入待核验清单。

## 5. 版式要求

- 采用黑白灰为主，必要时可使用浅色池标题，但交付图应保持统一、清晰、可打印。
- 节点宽高、间距、字体、边框尽量一致；文字应自动换行且不得溢出节点。
- 流程主线自上而下排列；同一时间或并行评估可并列放置。
- 避免节点重叠、结束节点压线、连线斜穿、过多回折、空白过大或长图不可读。
- 结果节点应独立呈现，并连接结束事件；结果文字应来自 F/I 列确认的成果、状态、报表、台账、归档或后续衔接。

## 6. 证据约束

- 阶段 3 只能读取阶段 2 核验后 Excel 中同一事项的处室、职责、事项、数字化结论、流程、系统和流程依据。
- 每个池、泳道、活动、网关、消息流、结果节点都必须能从 F/I/H 或明确备注中找到依据。
- 主体不明、流程起点不明、结果不明、跨主体消息不明、判断条件不明或退回路径不明时，不得用模板补造。
- 证据能够形成主流程但缺少异常路径时，可画主流程，同时在待核验清单中说明缺少的异常路径。
- 证据不能形成至少两个连续业务动作和一个明确结果时，不出图，列入待核验清单。

## 7. 交付校验

- Draw.io 文件可打开，且每个可出图事项一页。
- 图中系统未作为泳道主体；如系统作为池，池内泳道必须是用户角色或业务角色。
- 每页有标题、一个开始事件、活动节点、结果节点和结束事件。
- 判断分支、退回回流和消息流只在依据明确时出现。
- 导出的 PNG/JPG 清晰可读，并可嵌入阶段 3 Excel 的 G 列。
